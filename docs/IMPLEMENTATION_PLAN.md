# SOHTMON ERP 1.0 — план реализации

Мобильная ERP-система (PWA) для магазина: склад, продажи, долги клиентов, касса,
расходы, прибыль и сотрудники. Интерфейс на русском, валюты TJS и CNY.

## 1. Стек

| Слой | Решение |
|---|---|
| Фронтенд | Next.js (App Router, Server Components, Server Actions), TypeScript |
| Стили | Tailwind CSS, бело-синяя тема, mobile-first, нижняя навигация на телефоне |
| Графики | Recharts |
| Бэкенд | Supabase: Auth (email + пароль), PostgreSQL, PostgREST |
| Безопасность | Row Level Security на каждой таблице, роли в `profiles`, бизнес-операции в SQL-функциях |
| PWA | `manifest.webmanifest`, service worker, иконки, `apple-touch-icon`, safe-area для iPhone |

## 2. Принципы архитектуры

1. **Вся бизнес-логика, меняющая остатки и деньги, выполняется в PostgreSQL**
   (`create_sale`, `create_arrival`, `create_adjustment`, `add_customer_payment`,
   `cancel_sale`, `add_cash_operation`). Каждая функция — одна транзакция:
   нельзя продать товар и не списать остаток.
2. **Журналы неизменяемы.** Продажи, движения склада и кассы нельзя изменить
   или удалить напрямую — только сторнировать (отмена продажи создаёт обратные движения).
3. **Остаток = сумма движений.** `products.stock` обновляет только триггер
   журнала `stock_movements`; прямое изменение запрещено триггером.
4. **Себестоимость** — скользящая средняя в TJS, пересчитывается при приходе.
   В строке продажи сохраняется себестоимость на момент продажи → точная прибыль.
5. **Валюты.** У каждого денежного документа есть `currency` (`TJS`/`CNY`) и
   `rate` (сколько TJS за 1 единицу). Отчёты считаются в TJS. Текущий курс CNY
   хранится в `settings` и редактируется владельцем/админом.
6. **Роли проверяются дважды:** в UI (скрытие разделов, редирект) и в базе
   (RLS + проверки внутри SQL-функций). База — источник истины.

## 4. Схема базы данных

- `profiles` — сотрудник: ФИО, телефон, роль (`app_role`), активность. Создаётся триггером на `auth.users`.
  Первый зарегистрированный пользователь становится владельцем; остальные — неактивны, пока их не настроит владелец/админ.
- `settings` — одна строка: название компании, курс CNY→TJS.
- `categories` — категории товаров.
- `products` — артикул, штрихкод, название, категория, единица, закупочная цена + валюта,
  цена продажи + валюта, средняя себестоимость TJS, остаток, минимальный остаток, активность.
- `customers` — клиенты; view `customer_balances` — долг по каждой валюте.
- `sales`, `sale_items` — чеки (номер, клиент, валюта, курс, скидка, оплачено, долг, способ оплаты, статус).
- `stock_arrivals`, `stock_arrival_items` — приходы от поставщиков.
- `stock_adjustments` — инвентаризация, брак, потеря, возврат, начальный остаток.
- `stock_movements` — журнал всех изменений остатков.
- `customer_payments` — погашения долгов.
- `cash_transactions` — журнал кассы (приход/расход) по валютам; view `cash_balances`.
- `expenses` — расходы по категориям.

Индексы: поиск товара по названию/артикулу/штрихкоду (`pg_trgm`), даты документов, внешние ключи.

## 7. Ограничения тестовой среды

В среде разработки нет доступа к Docker-образам Supabase, поэтому:
- SQL (схема, RLS, функции) тестируется на локальном PostgreSQL 16 с эмуляцией
  схемы `auth` Supabase (`auth.users`, `auth.uid()`, роли `anon`/`authenticated`).
- Фронтенд проверяется сборкой, проверкой типов, линтером и скриншотами в Chromium.
- Полный сквозной сценарий (вход → продажа) нужно проверить на реальном проекте Supabase
  после подключения ключей; инструкция — в README.
